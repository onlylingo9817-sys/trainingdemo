# 知识点模块：数据结构与架构现状（供外部讨论用）

版本：v1.2 覆盖层 + UX v1.3
日期：2026-11-20
用途：给业务 / 产品 / 研发同事看清「现在是什么样」，并回答文末的疑问清单。
所有数字都是从当前 Demo 数据实测得到，不是估算。

---

## 一、一句话现状

知识点（68 条）是「学什么」的标准库；讲解 / 题 / 演练是「怎么教、怎么考」的资产；三者通过「知识点 ID」挂接。
目前**知识点带车型、资产几乎不带车型**，导致「一个知识点 = 一份讲解」的结构，多车型只能靠复制知识点来绕。

## 二、数据实体与字段

### 2.1 知识点 Knowledge Point（68 条）

| 字段 | 含义 | 现状取值 |
| --- | --- | --- |
| `id` / `code` | 内部 ID / 业务编号 | K1–K68 / `KP-SU7-05` 等 |
| `name` / `one` | 名称 / 一句话定义 | 名称必填；一句话定义 68 条都有 |
| `domain` | 知识域（5 个启用维度之一） | 品牌文化 / 产品知识 / 销售技能 / 政策权益 / 交付服务 / 客户运营 |
| `ability` | 能力项（销售动作） | 7 项；**产品知识为空** |
| `sellpoint` | 卖点分类 | 15 项；**产品知识必填** |
| `typeV12` | 类型 | 概念 / 卖点 / 技能 / 流程 / 政策 |
| `cars[]` | **适用车型** | 通用 42、车系 15、产品线 8、车型 2、多车系 1 |
| `roles[]` / `alsoRoles[]` | 适用岗位 / 兼用岗位 | 零售顾问 / 销售主管 / 店长 / 交付顾问 / 服务顾问 |
| `line` | 业务线 | 销售 / 交付 / 店长 |
| `batch` | 学习阶段 | B1-30 天 / B2-90 天 / B3-后续 |
| `stage` | 主要业务环节 | 9 个取值，「不直接对应」为默认 |
| `pri` | 优先级 | P0 50 条 / P1 18 条 |
| `assess{}` | 考核规格 | `anchorQ` 核心题数、`practiceQ` 练习数、`anchorDrill` 过关演练数、`pass` 过关线、`validityDays` 有效期 |
| `owner` / `ownerRole` | 业务负责人 / 角色 | 68 条都有负责人 |
| `st` / `statusV12` | 启用状态 / 依据核对状态 | 启用 / 停用；结构已核 / 内容待核 / 草案 |
| `cars` 之外的旧字段 `car`、`tags`、`dims` | 历史兼容 | 标签体系已取消，但仍留在数据里 |
| `pre[]` / `rel[]` | 先学（前置）/ 相关 | 各 62 条边 |
| `srcDoc` | 依据资料 ID | 部分为空 |
| `reviewDue` / `specVer` | 复核日 / 规格版本 | 政策类 30 天、技能 90、概念 180 |

**考核规则**：P0 且类型为技能/流程/卖点 → 要求 3 道核心题 + 1 场过关演练；概念/政策 → 3 道核心题、不强制演练。

### 2.2 内容（讲解 / 课程 / 话术，88 条）

| 字段 | 含义 | 现状 |
| --- | --- | --- |
| `kind` | 类型 | 课程 41 / 话术 47（讲解是内容的一种用途，不是独立类型） |
| `title` / `body` | 标题 / 正文 | 正文合计仅约 15 KB（演示占位稿，不是真实讲解） |
| `kps[]` | 挂载的知识点（**多对多**） | 88 条中 82 条挂了知识点 |
| `kpRole{}` | **每个知识点的用途** | `主讲解` / `补充材料`，按知识点分别存 |
| `mainKp` | 主讲解知识点 | **单值**，一条内容只能对一个点是主讲解 |
| `car` | 适用车型 | **单值**，54/88 填了；**不参与任何判定** |
| `tags[]` | 标签 | 旧体系 |
| `st` / `pubSt` / `pubVer` | 草稿 / 审核中 / 已定稿 / 已归档；上架状态 | — |
| `expire` / `vers[]` / `hist[]` | 有效期 / 版本快照 / 留痕 | — |

### 2.3 题（130 条）与演练（23 场）

| 字段 | 题 | 演练 |
| --- | --- | --- |
| 归属 | `kp`（**单归属**，转移不是共享） | `kp`（单归属） |
| 用途 | `role`：锚题（核心测评）/ 练习题 | `role`：锚定演练（过关）/ 练习演练 |
| 内容 | `stem`/`opts`/`ans`/`why` | `name`/`scene`/`persona`/`turns[]` |
| 来源 | `src`（必须指向已定稿讲解） | `src` |
| 状态 | `st`、`version`、`anchorSetVersion` | `st`、`scoringVersion` |
| **适用车型** | **无此字段** | **无此字段** |

实测：130 道题里 **47 道题面提到具体车型**（如「N70 的后备箱常规容积是多少」），但没有任何车型字段 → 会被当成「覆盖所有车型」的通用锚题。演练 23 场目前都与车型无关的场景居多。

### 2.4 周边实体

| 实体 | 关键字段 | 与知识点的关系 |
| --- | --- | --- |
| 补学任务 `tasks`（28 条） | `mid`、`kpId`、`level`（L2 口径变更 / L3 作废重大）、`state`、`due`、`specVer` | 一条任务 = 一个人 × 一个知识点 × 一个版本 |
| 课题 `topics`（9 条） | `kpId`、`st`、`flow`、`sug` | 课题 → 知识点（可回写） |

| 人员 `people`（41 人） | `tier`、`hireDate`、`store`、`region`、`roles[]` | 岗位画像与就绪度按人算 |

## 三、指标口径（现状）

| 指标 | 分母 | 分子 |
| --- | --- | --- |
| 覆盖度 | 岗位 × 车型 × 学习阶段 × P0/P1 命中的知识点数（SU7 Pro + P0 = **33**） | 有核心讲解（该知识点至少 1 条 `主讲解`、已上架、未过期） |
| 可授课率 | 同上 | 有讲解且依据核对状态不是「内容待核」 |
| 可考核率 | 同上 | 核心题 ≥ 3 且（需要时）过关演练 ≥ 1 |
| 时效健康度 | 有核心讲解的点 | 未过期、未超复核日 |

**关键局限**：分子只看「这个知识点有没有讲解」，**不看这条讲解适用于哪个车型**。实测同一条知识点在 `SU7 Pro` 与 `SU7 Ultra` 下指标完全相同。所以：
- 一条「SU7 底盘」讲解，会让「YU7 底盘」这个点如果共用同一条知识点时也被算作有讲解；
- 反过来，按车系拆成两条知识点时，各自只有一条讲解，看似都对，实际是重复维护。

数据校验：68 条中 **0 个结构错误、48 条缺口提示**（缺讲解 / 缺考核规格 / 时效待处理）。

## 四、架构现状

### 4.1 运行形态

- 纯前端、无构建、无依赖；`src/index.html` 顺序加载 **34 个脚本** + 2 个 CSS。
- 单页应用：无路由，`UI.page` 决定渲染哪个页面；`render()` 一次性重绘 `#main`，模板是字符串拼接。
- 交互：全站事件委托，`data-act`（点击）/ `data-wc`（change）/ `data-kf`（表单输入）。
- 数据：全局对象 `S`，落在 `localStorage` 的 `trainingdemo.save.v1`（字段白名单 23 个）。
- 演示数据确定性生成（同一天打开，数字一致）。

### 4.2 脚本分层

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 内核 | `a_core.js` | 工具、`S`、存储、日期、toast、弹窗 |
| 页面 | `b_pc1 / c_* / d_pc3 / e_pc4` | 工作台、内容、项目、效果、配置中心 |
| 知识点 v1 | `o_catalog / x_taxonomy` | 旧知识点页面与 v1 标准库 |
| 知识点 v1.2 | `x_kp_v12.js` | **覆盖层**：68 条标准库、字典、四指标、锚练分流、UI 覆盖 |
| 知识点 UX | `y_kp_ux.js` | 信息层级、操作路径、空 / 加载 / 报错、表单校验（本轮新增） |
| 内容 / 题 / 演练 | `k_content / k2_edit / k3_import / p_quiz / r_drill` | 内容与资产维护 |
| 评审 | `review_gray.js` | 评审单、投票、代录、超期 |
| 零售通 | `f_rn / w_rn_extra` | 手机端 |

### 4.3 必须知道的机制：后加载覆盖

同名函数/方法**后加载的生效**。当前有 **35 个名字被覆盖定义**：

- `x_kp_v12.js` 覆盖了 19 个（如 `kpHealth`、`kpLibrary`、`kpOverviewNew`、`pageHelp`、`v23Seed`）
- `y_kp_ux.js` 覆盖了 15 个（如 `kpCands`、`kpOpen`、`kpMasteryCard`、`A.kpCandOk`、`A.kfSave`）
- `g_topic3.js` 覆盖 1 个

**风险**：改到被覆盖的旧定义会「改了不生效」；历史上已发生多次（交接文档 §34 记录删过一批死代码）。新增功能的正确位置是：业务规则进 `x_kp_v12.js`，展示与交互进 `y_kp_ux.js`。

### 4.4 校验与测试

- `npm run check`：34 个脚本顺序、语法与启动链。
- `npm test`：83 组 headless Chrome 探针，83/83 通过。
- `npm run build`：导出单文件供对外分享（dist 不提交）。

## 六、需要你带出去确认的疑问

> 建议按编号回答，A / B / 或直接写结论都可以。每题都写了「为什么问」和「不同答案会导致什么」。

### A. 知识点与车型的关系

**A1. 知识点是否应保留「适用车型」？**
- 备选：① 保留（作为应覆盖范围，算分母）② 删除（车型完全交给内容）③ 保留但只做筛选标签
- 为什么问：若删除，就无法回答「卖 SU7 的顾问该会哪些点」，完备度分母只能从内容反推，会永远接近 100%。
- 我的建议：保留，但只用于分母 / 画像 / 选人，不再承担「内容绑定」。

**A2. 底盘与安全是不是一个知识点？**
- 我的判断：底盘（驾控）和安全是两个不同学习结果，应分两条；但两条都采用「1 个知识点 + 每车型一条讲解」。
- 需要确认：业务上是否认同「驾控」与「安全」分开考核。

**A3. 哪些知识点应合并？**
- 现状有 6 组按车系复制：底盘与驾控（SU7 / YU7）、外观设计、续航补能、智能座舱、安全、车型定位。
- 需要确认：合并后原来两条的题、演练、补学任务如何归属；澎程是否与 SU7/YU7 合并。

### B. 资产是否带车型

**B1. 讲解（核心讲解）是否必须绑定车型？**
- 备选：① 必填，且可多车型 ② 可空（空=所有车型通用）③ 保持现状（单值、不参与判定）
- 我的建议：必填 + 多值，默认继承知识点车型。

**B2. 核心测评题是否必须绑定车型？**
- 关键点：锚题决定「该车型能不能考核」。现在 47 道题明确提到车型却无归属。
- 需要确认：车系级（SU7）够不够，还是要到版本级（SU7 Pro / Ultra）。

**B3. 情景演练是否需要绑定车型？**
- 现状：23 场都与车型无关或少有关。
- 需要确认：「试驾路线 / 配置讲解」类演练是否要按车型分别维护；「价格异议 / 邀约」类是否统一通用。

**B4. 课程与话术是否与讲解用同一套车型字段？**
- 现状：课程 41 门、话术 47 条，共用一个「内容」实体。
- 需要确认：课程是「受众车型范围」，话术是「讲的就是这台车」，两者语义不同，是否要拆成两个字段。

### C. 口径与主讲解

**C1. 一个知识点允许有几条「主讲解」？**
- 备选：① 只能 1 条 ② 每车型各 1 条（多车型就有多条）③ 不限，另设 1 条默认
- 需要确认：多条时谁定默认、谁来维护。

**C2. 一条内容能否同时是多个知识点的主讲解？**
- 现状：不能（`mainKp` 单值）。
- 场景：一条「SU7 全系讲解」覆盖 5 个知识点，目前只有 1 个算有讲解，另外 4 个进缺口清单。

**C3. 主讲解过期 / 下架后如何交接？**
- 现状：该知识点立刻变成「缺讲解」，没有接任机制。

### D. 指标与治理

**D1. 完备度是否要按车型分别计算？**
- 现状：分子不看车型，同一知识点对所有车型结果相同。
- 需要确认：这是不是业务想要的「按车型看覆盖」。

**D2. 补学任务是否按车型拆分？**
- 现状：任务 = 人 × 知识点 × 版本，不含车型。
- 需要确认：SU7 讲解更新时，只卖 YU7 的顾问要不要补学。

**D3. L2 / L3 变更级别是否要区分车型影响面？**

**D4. 评审单是否需要车型维度？**
- 现状：评审单只对「内容或知识点」发起，不区分车型。

### E. 架构与交付

**E1. 是否接受「后加载覆盖」这种写法长期存在？**
- 现状：35 个名字被覆盖，改错位置会静默不生效。
- 备选：① 继续（成本低、风险可控）② 按功能拆模块、去掉覆盖 ③ 迁到构建工具 / 框架。

**E2. 是否需要真实后端与接口？**
- 现状：全前端 + localStorage，演示数据确定性生成。

**E3. 单文件导出是否继续作为对外交付方式？**
- 现状：`dist/` 单文件用于不方便起服务的人体验；本轮出现过「打开旧 dist 以为没改」的问题。
